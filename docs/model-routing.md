# Jev-first typed model routing

Live engine requests start with TypeSafe Jev. Jev receives the current objective, observation and bounded action catalogue, and returns a typed handler choice (`jev` or `jev_router`) together with the ordinary Jev action answer. If the route's own chosen probability is absent or below the run's own floor, the request is blocked without executing either action. The floor is measured on that route probability, not on the handler's self-rated confidence: a self-rating is recorded and shown to Jev, but it is not a mechanical invalidity, so a low one must never silently discard an answer the engine can actually carry out. That floor is a per-run setting (`--route-min-confidence`, default `0.5`) rather than a constant baked into the engine, because a run must not be stopped by a threshold tuned on someone else's evidence; the floor a run actually used is reported in its session summary. It is a policy threshold, not a calibrated correctness guarantee.

When Jev selects `jev`, its action is consumed from that same TypeSafe request; the route and action are not separate calls and their shared usage is counted once. When Jev selects `jev_router`, the engine makes one follow-up OpenRouter Chat Completions request to `typesafe/jev-router`, using the same observation and candidate catalogue. The request disallows tools and requires a strict JSON-schema object containing exactly one candidate ID. Router output supplies no action probabilities or confidence. Jev Router is a deeper-reasoning escalation over the supplied evidence; it has no additional game-world access. See the [Jev Router model page](https://openrouter.ai/typesafe/jev-router), [Chat Completions API](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request), and [structured outputs guide](https://openrouter.ai/docs/guides/features/structured-outputs).

The TypeSafe credential is `TYPESAFE_API_KEY` (or the configured key file). Escalation additionally requires `OPENROUTER_API_KEY`; an OpenAI key is not used. The engine allows at most one TypeSafe request and one OpenRouter request per decision, with a shared 10-second deadline and no retries or recursive routing. It reserves up to two request-budget slots when both credentials are present, otherwise one. Completed outcomes refund confirmed unused reservations; cancellation retains uncertain reservations. If Jev chooses escalation but the OpenRouter key or a second budget slot is unavailable, no action runs: that answer is dropped and the paced loop may ask again, so a single escalation the run cannot perform does not end the session.

Missing or sub-floor routing confidence blocks that answer: it is recorded as a rejected answer, no action runs, and the paced loop may ask again from the next observation within the remaining session budget — a live run must not end because one answer was unsure. Credential, transport, HTTP and deadline failures remain fatal. A malformed, refused, tool-call, truncated, missing or out-of-catalogue response is rejected and never executed; rejected answers are recorded and the paced continuous loop may ask again within the remaining session budget. Credential, transport, HTTP and deadline failures block the attempt and fail or pause the session. No failure path falls back to a different model or invents a choice.

Before dispatch, the engine also requires the answer to remain current: the request generation and observation age must pass the configured freshness bound, the latest connected observation must be no more than one second old and must match the same world epoch and dimension, health must not have fallen, position must not have moved more than 1.5 blocks, and the selected target or skill must still be valid. A stale answer is dropped (or, when the safety reflex has already handled intervening damage/knockback, rejected so the paced loop can request again). These guards are independent of model confidence and do not prove that an accepted action will reach its goal.

`model_route` and `model_stage` telemetry record the selected route, attempts, status, latency and usage. Each stage records the requested model; the OpenRouter stage may additionally include its validated provider-reported served model. The requested identity remains `typesafe/jev-router` even if OpenRouter reports a different served model. The returned decision and action origin stay `JEV-ROUTER-SELECTED`, making the requested handler auditable separately from provider dispatch. TypeSafe decisions are labelled `JEV-SELECTED`. The decision-bearing dispatch row carries the decision and is labelled by model identity. The later accepted `action` row has no decision object: its message preserves the origin, and `JEV-ROUTER-SELECTED` is recognized there. The classifier maps a decision-less accepted Jev action to `JEV-SELECTED` from its preserved origin message; route-choice events themselves have no action origin. The UI timeline and `recording-report` use the same origin classifier.

Historical recordings that contain Astra decisions remain readable and retain their historical Astra model identity and origin label. Astra is not a handler in the current live routing path. The fixture remains synthetic and provider-free. Live TypeSafe Jev handler calls are recorded (`runs/level1-resume/live-turn23.json`, test-server telemetry: `jev-latest` requests, 4,935 input and 107 output tokens at 299ms, handler judgment uncertain at confidence 0.02, no action executed). No live `typesafe/jev-router` escalation call and no complete autonomous Minecraft Level 1 wood sequence has been verified; see [current demonstrable behavior](current-demo.md). Do not treat offline checks, a fixture arrival, or accepted actions as live gameplay proof.
